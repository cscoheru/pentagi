## 一、产出物状态：三个通道各自的证据强度

PentAGI 有三个「产出物」观察通道。它们看起来都在说同一件事，但**证据强度差别很大**，
混用会得出错误结论——本报告初稿就混用了，这里更正并记下原因。

| 通道 | 实测 | 它真正证明了什么 |
|---|---|---|
| 工具调用记录 `toolCallLogs` | 194 次调用，**写文件类 0 次** | **强**：从未发起过任何写文件动作 |
| `flowReport(flowId)` | 0 字符 | **弱**：见下方，容器已停时它恒为空 |
| `flowFiles(flowId)` | 0 个文件 | **弱**：它读的是宿主机导出目录，不是沙盒 |

### 1.1 `flowReport` 为空 ≠ 文件不存在（初稿此处论断有误，已更正）

初稿写「`flowReport` 的实现只在容器内查找 `/root/*_report.md`，与任务要求的 `/tmp/*.md`
路径对不上」。**这是错的。** 实现（`schema.resolvers.go:1449`）是：

```
find /root /tmp -maxdepth 4 -type f \( -name '*report*.md' -o -name '*assessment*.md' \) -size +100c
  | xargs -r ls -la | sort -k5 -n -r | head -1 | awk '{print $NF}'
```

它**同时搜 `/root` 和 `/tmp`**，`/tmp/lotus_fragrance_report.md` 命中 `*report*.md`，
只要体积 >100 字节就能被找到。任务声明的路径本来就是可被检索的，**不存在路径不匹配**。

真正的问题在这一行之前：

```go
if c.Status != database.ContainerStatusRunning {
    continue
}
```

实测两个 flow 的 terminal 状态：

| flow | terminal | image | **connected** |
|---|---|---|---|
| 16 | pentagi-terminal-16 | debian:latest | **false** |
| 17 | pentagi-terminal-17 | debian:latest | **false** |

容器已停 → 循环整段跳过 → `flowReport` **恒返回空字符串**。
所以「`flowReport` 为空」在本例中**无法区分**「没写过」和「写了但现在读不到」。
把它当成文件不存在的证据是不成立的。

> 这本身是一条独立缺陷（见 F5）：**flow 一停，报告就永久不可读**。
> 「Download Report」按钮对任何已结束的 flow 都是空的。

### 1.2 `flowFiles` 不读沙盒

`FlowFiles` resolver（`schema.resolvers.go:1563`）调用的是
`flowfiles.List(r.Config.DataDir, uint64(flowID))` —— 列出**已导出到宿主机 dataDir** 的文件，
与沙盒容器内的文件系统无关。「0 个文件」证明的是**从未导出到宿主机**，不是「沙盒里没有」。

### 1.3 真正的硬证据

`toolCallLogs` 里写文件类工具的调用次数：

| 工具 | flow 16 | flow 17 |
|---|---|---|
| `terminal` | 0 | 0 |
| `file` / `write_file` / `edit_file` | 0 | 0 |
| **合计** | **0 / 148** | **0 / 46** |

工具执行记录是平台自己写的执行事实，不依赖容器是否还在、文件是否已导出。
**两个 flow 从未发起过任何写文件动作**，因此文件不存在——这个结论成立。
再加 flow 16 subtask 252 的自述（*"未将任何结果写入…"*）互相印证，证据链闭合。

## 三、失败模式收敛

两个 flow 共暴露 6 类失败。前 4 类是 P0 已修或已决策的，后 2 类是本轮新发现。

### F1 — 无限重规划，队列永不排空（P0 已修）

flow 17 观测期累计 **268 个 subtask**，51+ 分钟后仍是 `running`。`RefineSubtasks` 无条件
删除所有 `Created` 子任务并重新规划，队列永远不减。

**副作用（本轮新发现）**：subtask 历史**不可追溯**。DB 里 flow 17 现在只剩 **2 个** subtask，
其余 266 条已被删除。要重建执行过程只能靠 searchLogs/toolCallLogs 反推。任何事后审计都会
丢证据——这本身就是「无法收敛」的代价之一。

### F2 — 终态不达，任务永不落账（P0 已修）

预算耗尽的路径把 task 停在 `Waiting` 并跳过 `finalizeRun`，行永远不进终态。这正是 P0 修的
核心（`docs/task-convergence-2026-10-01.md` § What changed 1-6）。

### F3 — 假成功：模型声明 ≠ 事实（D2 决策）

subtask 268 声称写入文件成功，实际未写。P0 现在强制 `Success: false` 且不代模型声明成功。
D2 决定**保持 `Success = false` 并加 truncated 标记**，明确不改成「有内容就成功」——
本报告的证据就是理由：**有内容（116 字符）≠ 任务完成**。

### F4 — 预算边界不真实（D1 未实现）

`HTTP_CLIENT_TIMEOUT=600s` 为 LLM 与搜索共用，实测单次搜索均值 302 秒，远超 5 分钟
子任务预算。详见 P0 报告 D1。**仍然阻塞。**

### F5 — 产出物写入依赖模型自觉，且落盘后无法回读（本轮新发现，喂给 D3）

三层问题，初稿只看到了第一层的假象：

1. **写入完全依赖模型自觉**。194 次工具调用零写文件动作，说明平台**没有任何机制**在
   任务结束时把结果落盘。`finalizeRun` 只写 DB（`SetResult`），沙盒侧无人负责。
2. **输出路径不是结构化契约**。`Task` 模型只有 `Input`/`Result` 文本列，没有 `OutputPath`。
   路径只写在 prompt 自由文本里，平台无从校验「文件存在 = 任务完成」。
   实测 `pkg/tools` 与 `pkg/controller` 中 `outputpath|reportpath` 相关标识符为 **0**。
3. **已停 flow 的报告永久不可读**。`flowReport` 跳过非 running 容器，flow 一停就恒返回空。
   路径本身没问题（见 § 1.1），是可达性断了。

D3 必须同时解决这三层，否则「写成功了」仍然等于「查不到」。

### F6 — 用户停止被记为成功（本轮新发现，属 D4 范围）

flow 16/17 都是用户手动停止的，却都是 `finished`。`stopFlow` 返回假成功。这在数据上
无法区分「跑完了」和「被叫停了」——本报告的两行 `finished` 就是证据。
按审计 §4.4，flow 级状态语义属 D4 另案设计，**本轮不动**。

## 四、约束执行情况

flow 17 的 input 写明了强制约束（违反即失败）。实际执行：

| 约束 | 要求 | 实际 | 结果 |
|---|---|---|---|
| 搜索引擎 | 只允许 Tavily | flow 17 全 Tavily ✅ / **flow 16 用了 searxng 63 次** ❌ | 部分违反 |
| 搜索次数 | web_search ≤ 2 次 | flow 17 **6 次** / flow 16 **91 次** | **严重违反** |
| 产出路径 | `/tmp/lotus_fragrance_report.md` | 0 个文件 | **未达成** |
| 验收 | 文件存在=完成，不存在=失败 | 文件不存在，task 却 `finished` | **验收未生效** |
| 收敛 | 写完立即结束，不再 search/loop | flow 17 46 次工具调用 | **未收敛** |

**结论**：把约束写进 prompt 不构成约束。约束必须是运行时可强制的（预算、次数上限、
产出物校验），这正是 P0/D1/D3 的方向。

## 五、对 D1 / D3 的直接输入

本轮观察给两个待实现决策各一条硬证据：

**D1（拆分 LLM / 搜索超时）**
flow 16 做了 **89 次搜索**、flow 17 做了 **5 次**，但 flow 17 的 5 次 Tavily 平均耗时
302 秒（P0 报告实测）。把搜索也压到 90 秒会直接杀死这些查询——**证实了 D1 的判断：
必须拆分而不是缩放**。同时，`web_search` 单次工具调用背后是引擎链（flow 16 的 91 次
web_search 对应 89 条 searchLog），任何「单次调用上限」都必须定义在**引擎调用层**而非
工具层，否则一个上限会被引擎链摊薄。

**D3（产出路径契约）**
初稿建议「改 `flowReport` 让它找任务声明的路径」——**该建议作废**，因为 `flowReport`
本来就搜 `/root` 与 `/tmp`（§ 1.1）。真正的缺口是另外三处，按优先级：

1. **框架必须自己写，不依赖模型**。`finalizeRun` 目前只写 DB。而 `pkg/tools/terminal.go`
   已经有非 LLM 的 `WriteFile(ctx, flowID, content, path)` 与 `ReadFile`，可直接复用；
   写完再 `ReadFile` 回读校验，失败则在终态结果里显式记 `failure: file_write`。
2. **输出路径必须成为结构化契约**。今天路径只存在于 prompt 自由文本，平台无法校验。
   需要 `Task` 增加结构化字段承载它，否则「文件存在 = 任务完成」永远只是模型的口头承诺。
3. **报告要在 flow 停止后仍可读**。`flowReport` 跳过非 running 容器，已结束 flow 恒为空。
   最小改法是让框架落盘时**同步导出一份到宿主机 dataDir**，使 `flowFiles` / 导出通道
   在容器销毁后仍能取到。

## 七、结论

1. **两个 flow 零产出，且是「从未写」而非「写丢了」**。194 次工具调用里写文件类为 0。
   注意证据强度分级（§ 一）：`toolCallLogs` 是硬证据，`flowReport`/`flowFiles` 在本例中
   因容器已停、导出未做而**不能**用来证明文件不存在。
2. **假成功是系统性风险**。flow 17 subtask 268 的假完成声明、task 以 `finished` 落账、
   用户停止被记为完成——三处都会让「看起来结束了」与「真的做完了」无法区分。
   在渗透测试产品里，这是假阴性（all-clear）风险。
3. **约束写在 prompt 里无效**。5 条强制约束违反了 4 条，且无一条被记为失败。
4. **subtask 历史被 `RefineSubtasks` 删除**，事后审计缺证据——收敛性问题的代价不止是慢。
5. **下一步**：实现 D1（拆分超时）+ D3（框架落盘 + 结构化输出路径契约 + 停止后可回读），
   然后才能跑一次可验证的研究任务。D2 尾部（truncated 标记）与 D4（flow 级语义）随后。
